## 2026-11-20 — Spec review

- **4. `CORS_ORIGIN` is a comma-separated list**, starting as `http://localhost:3000`; the Vercel URL is added after the first deploy (02 §8, 03 §12). Why: `env.ts` requires it at boot, before the frontend URL exists.
- **5. Supabase: RLS on every table with no policies, and the Data API off** (02 §3). Why: belt and braces; `users.password_hash` must never be readable with the anon key, and either measure alone depends on one setting staying right.
- **6. Tooling approved** (02 §2, 03 §2): Node 26 (current LTS, pinned in `engines` and `.nvmrc`), ESM, `typescript`, `tsx`, `@types/*`, ESLint with `typescript-eslint`, `supertest`, `node --env-file` instead of `dotenv`; Tailwind 4 as installed by `create-next-app`. Why: unit 1 cannot start without them, and `--env-file` saves a dependency.
- **7. One env file per package**: `backend/.env` and `frontend/.env.local` (git-ignored), each with a `.env.example`; the root `.env.example` goes away (02 §8, 03 §12). Why: the repo had three files with mixed contents and no rule for which one loads.
- **8. `/health` answers 200 while the process is up, with `db: false` when `select 1` fails**; the cold-start screen then stops waiting and shows the generic error (02 §7, 03 §8). Why: a 503 would keep Render from bringing a deploy live and leave the waiting screen spinning forever.
- **9. `TRUST_PROXY_HOPS` is measured in work unit 3, with the `/auth` rate limit**, not at the first deploy (02 §4). Why: the number only matters once the rate limit exists.
- **10. Added `npm run migrate` (`scripts/migrate.ts`) to the backend and `npm run test` to the frontend** (CLAUDE.md, 02 §2, 03 §11). Why: 02 §3 already used `migrate` and 03 §11 already asked for `format.ts` tests.
- **11. `app.ts` exports `createApp(deps)` from unit 1** (02 §2, §9). Why: route tests need in-memory repositories; building it in from the start avoids rewriting the app in unit 3.
- **12. `daily_closes.close` is `numeric(18,6)`, not `numeric(14,4)`** (02 §3). Why: the provider sends 5 decimals and old split-adjusted prices are a few cents, so 4 decimals lose precision.
- **13. The Play top bar reads streak and round count from `GET /stats` on load**, then takes the streak from each decision response (03 §5.3). Why: `POST /rounds` cannot carry them without breaking the no-leak rule, and no spec said where they came from.
- **14. Name and sector come from `universe.ts`; the exchange comes from `meta.exchange` in `time_series`** (02 §5.5, 03 §3). Why: `symbols.exchange` had no source.
- **15. Large spin-offs left out of the universe; small ones stay and are listed as a known limitation** (01 §12). Why: prices are adjusted for splits only, so a spin-off can show as a fake drop; filtering the small ones (MRK, PFE, BIIB, APD, O) would thin the universe for a minor effect.
- **16. The reveal card shows `Precios ajustados por splits.` below the prices, muted** (03 §5.3). Why: an adjusted price (NVDA at about USD 4 in 2019) contradicts what the user remembers; the note belongs next to the number, not in the stats small print.
- **17. Acceptance criterion 8 (first chart in 30 s) is measured with the backend awake** (01 §13). Why: a cold start alone can take about a minute on the free host.
- **18. The spec review session is logged as `prompts/sessions/00-spec-review.md`** (01 §15). Why: it happened before unit 1, whose log is `01-setup.md`.

## 2026-11-20 — Work unit 1 (`odd/tasks/01-setup.md`)

- **Node 24 instead of Node 26** (replaces that part of point 6; 02 §2). Why: Render's docs make 24 the default for new services and never mention 26; the author chose not to wait for a failed deploy to find out.
- **pnpm 10 instead of npm** (02 §2, §3, §5.5, §10; 03 §11; CLAUDE.md). Pinned with `packageManager`, one lockfile per package, no workspace. Render's docs do not mention pnpm, so its build enables corepack; Vercel reads `packageManager` and installs with pnpm 10.33.0 on its own. Why: the author's choice of package manager.
- **Correction to the line above: no `ENABLE_EXPERIMENTAL_COREPACK` on Vercel.** The first plan set it; the first build then could not enable corepack from the `frontend` Root Directory and fell back to a pnpm older than 9, which failed. Without the variable, Vercel logged "generated by pnpm@10.x from package.json#packageManager pnpm@10.33.0" and the install worked.
- **TypeScript pinned to 6.0.x in the backend** (`~6.0.3`). Why: the npm `latest` tag is 7.0, and `typescript-eslint` 8.73 only supports `>=4.8.4 <6.1.0`, so `pnpm lint` would not run on 7.
- **Database TLS is verified against Supabase's root certificate** (`backend/certs/supabase-ca.crt`, "Supabase Root 2021 CA", public, valid to 2031), not just encrypted (02 §3, `src/db.ts`). Why: verifying the server costs one committed file; encrypting without verifying would accept any certificate. `DATABASE_URL` must not carry `sslmode`, because pg lets it override the `ssl` option.
- **`GET /health` renamed to `GET /status`** (01 §15; 02 §7, §10; 03 §8; `HEALTH_PATH` in `backend/src/routes/health.ts` and `frontend/src/lib/api.ts`). **The rule:** `||onrender.com/health` in EasyPrivacy (`easyprivacy/easyprivacy_thirdparty.txt`), a list Brave Shields applies by default and uBlock Origin enables by default. It blocks every cross-site request to a `*.onrender.com/health…` path, so `/healthz` would be blocked too. **How it was checked:** on the author's phone (Brave on Android, Shields on) the provisional page on the production domain showed "Failed to fetch"; the same URL opened directly showed the JSON, and with Shields off the page showed the response. A search of the public filter lists found the rule. A rough matcher over EasyPrivacy and EasyList (about 104k network rules, filtered by request type and options) blocked only the `/health*` paths among the routes of 02 §7. **Why `/status`:** it matches no rule in those lists and still says what the endpoint reports. The path lives in one constant per side, so another rename is one line in each package. **Why not proxy the API through Vercel:** it would sidestep every list, but Render would see Vercel's servers as the client, so unit 3's per-visitor rate limit would depend on trusting Vercel's forwarded header and a re-measured proxy count; every request would gain a hop; and the only blocked path is this one.
- **Supabase moved from `us-west-2` (Oregon) to `us-east-1` (North Virginia)** (A2, T13). **Why the regions must match:** every request that reads the database makes one or more sequential round trips from Render (Virginia) to Postgres; across the continent each one costs tens of milliseconds, inside one region a few. **What moved:** a new free project, `guess-up-east`, in `us-east-1` with the Data API off; the schema applied with `pnpm migrate` over TLS verified against the same committed root CA; `DATABASE_URL` replaced in `backend/.env` and on Render. The old project held only the schema. **Times,** measured from the author's machine in Argentina against the deployed `/status` with Render awake: before, 0.459 / 0.369 / 0.347 s (median 0.369 s; the no-database route `/does-not-exist` 0.283 s, so about 90 ms of database); after, 0.285 / 0.331 / 0.238 s (median 0.285 s; no-database 0.219 s, about 66 ms). Over 15 interleaved pairs after the move, `/status` minus the no-database route has a median of 11 ms. Three samples per side are noisy, and the before figure has only those three.
- **Client errors keep their status and are logged without their content; two error codes added** (02 §7, §8; T14). The independent verifier found that malformed JSON answered `500` and that the handler logged the parser error whole, raw body included, so a malformed login would have written a password to the logs. Now a 4xx answers with its own status and our own message and logs only status and type; a 5xx logs the stack. `413` and `415` had no code in 02 §7; the author chose to add `PAYLOAD_TOO_LARGE` and `UNSUPPORTED_MEDIA_TYPE` instead of reusing `VALIDATION`, which would have stopped meaning only 400 and shown the login's validation text for an unrelated problem.
- **Database timeouts: 2 s for the health check only; 10 s to connect and 30 s per query everywhere else** (02 §3, §7; T15). The independent verifier found that a database which accepts the connection and never answers made `/status` hang forever, because pg has no timeouts by default. Render's health check passes only on a 2xx or 3xx within 5 seconds (render.com/docs/health-checks), so `/status` gives up on the database after 2 s and answers `db: false`, leaving margin for the network. The pool's general bounds are much longer because the seed writes about 5,000 rows per symbol in one transaction; they only exist so a hung query eventually frees its connection. Checked with the real pool against a TCP server that never replies: `200 {"ok":true,"db":false}` in 2,025 ms.
- **SSL parameters in `DATABASE_URL` stop the process; `rejectUnauthorized: true` is explicit** (02 §3; T16). The independent verifier showed that the "no `sslmode`" rule above was not enforced: pg merges the parsed connection string over the `ssl` option, so `sslmode=disable` or `ssl=0` connect in plaintext, `no-verify` accepts any certificate, `require`/`verify-full` drop the pinned CA, `sslrootcert` swaps it, and `NODE_TLS_REJECT_UNAUTHORIZED=0` turned verification off. `createPool`, the only connection factory for the server, `migrate` and the seed, now refuses any `ssl…` or `uselibpqcompat` parameter and names it without the URL or values. Checked: 8 tests; boot with `sslmode=disable` exits 1 naming `sslmode`; with `NODE_TLS_REJECT_UNAUTHORIZED=0` a self-signed fake Postgres is still refused (`DEPTH_ZERO_SELF_SIGNED_CERT`). The local `DATABASE_URL` carries no query parameters at all.
- **`CORS_ORIGIN` entries must be exact origins, or the server does not start** (02 §8; T17). The independent verifier found that a trailing slash, a path, uppercase, `*` or a list left empty by stray commas all passed validation and then matched nothing, so every cross-origin request was blocked with no error anywhere. Each trimmed entry now has to satisfy `new URL(o).origin === o`, and empty entries or an empty list are refused; the message names the bad entry. Origins are not secrets, so printing the entry is acceptable here, unlike the other variables. The value on Render as the author reported it (`http://localhost:3000, https://guess-up-frontend-kappa.vercel.app`) passes.
- **Two development dependencies outside the approved lists, kept** (T18). `@eslint/js` (backend): the typescript-eslint flat config of 02 §2 imports ESLint's recommended rules from it, so the approved "ESLint with `typescript-eslint`" needs it. `@tailwindcss/turbopack` (frontend): `create-next-app` 16.4.6 installs it and wires it in `next.config.ts` as Tailwind 4's loader for Turbopack, and 03 §2 approves the Tailwind that `create-next-app` installs. Found by the independent verifier.
- **PENDING, deferred by the author: revoke the default privileges of `anon` and `authenticated`** (T19; for the README section on improvements, "what I would do next"). Found by the independent verifier; deferred on 2026-11-20.
  - **State found** (read-only, project `guess-up-east`, 2026-11-20): `anon` and `authenticated` hold `DELETE, INSERT, REFERENCES, SELECT, TRIGGER, TRUNCATE, UPDATE` on `users`, `symbols`, `daily_closes`, `rounds` and `api_usage`. The default privileges of schema `public`, both for objects created by `postgres` and for objects created by `supabase_admin`, give them every table privilege (`arwdDxtm`), `rwU` on sequences and `EXECUTE` on functions.
  - **Why it does not block today, from what was checked:** RLS is enabled on the five tables with no policies (`pg_class.relrowsecurity` and `pg_policies` after the migration); the Supabase security advisors report only the INFO lint `rls_enabled_no_policy` on those tables; a Data API request with the publishable key returned `503 PGRST002` and no rows; the author turned the Data API off in the dashboard. The probe answers the same with the API on or off, so the off state rests on the dashboard.
  - **Proposed `backend/sql/002_revoke_data_api_roles.sql`,** following Supabase's "Securing your API" (default privileges for an existing project):
    ```sql
    revoke all on all tables in schema public from anon, authenticated;
    revoke all on all sequences in schema public from anon, authenticated;
    alter default privileges for role postgres in schema public revoke all on tables from anon, authenticated;
    alter default privileges for role postgres in schema public revoke all on sequences from anon, authenticated;
    alter default privileges for role postgres in schema public revoke execute on functions from anon, authenticated;
    ```
  - **Plan for `migrate`:** a `schema_migrations` table (`filename`, `applied_at`) with RLS enabled; a one-time baseline that records `001_init.sql` as applied without running it when `public.users` already exists (production); every pending `sql/*.sql` applied in name order, each in one transaction together with its record, rolling back and stopping on error; a second run finds nothing pending and says so. The choice of what to apply lives in a pure function with its own test. 02 §3 would gain the bookkeeping table.
  - **Limits noted with the proposal:** (1) the defaults owned by `supabase_admin` cannot be changed from the `postgres` role; tables created by `migrate` are owned by `postgres`, so they are covered. (2) Supabase's docs also revoke from `service_role` and, for functions, from `public`; left out because they were not asked for. (3) The two `revoke all on all …` statements are no-ops when repeated.
- **The seed stops at the daily credit cap instead of waiting** (02 §5.3; unit 2, A3). `acquire()` waits for the next minute slot, as specified, but throws `DailyBudgetExhaustedError` when the 750-credit day is used up: waiting until 00:00 UTC is not useful for a script run by hand, and the seed is resumable, so a later run continues where it stopped. The daily counter is one atomic upsert in `api_usage`.
- **How the two rejection rules of 02 §5.2 combine** (unit 2, T5). The spec did not say whether "fewer than 400 bars" counts before or after the latest bar is dropped, or whether a bad close in that dropped bar counts. Chosen: every close of the response must be positive, the latest included (a zero there is as suspicious as anywhere else), and at least 400 bars must remain after the drop, so what is stored always meets the minimum. Written test-first in `domain/series.ts`, which 02 §2 now lists.

## 2026-11-20 — Work unit 3 (`odd/tasks/03-auth.md`)

- **No refresh token; one access token valid for 7 days** (02 §4). Why: a game with no money in it does not justify a second token, its storage and its rotation. Cost: a stolen token works until it expires, and logging out only forgets it in that browser.
- **No email verification and no password reset** (02 §4, §11). Why: out of the three-hour budget. Cost: anyone can register an address they do not own, and a forgotten password means a new account.
- **The password limit is counted in bytes: at least 8 characters, at most 72 bytes in UTF-8** (02 §4; A4). The spec said "8 to 72 characters". bcrypt only reads the first 72 bytes, and `ñ` or an accented letter takes two, so a 72-character password could have a tail that does not count. Counting bytes rejects such a password instead of silently ignoring its end. For a password in plain ASCII nothing changes.
- **Login does not hide whether an email exists** (02 §4; A5). Both cases answer the same `401 INVALID_CREDENTIALS`, but an unknown email skips bcrypt and answers about 100 ms sooner. Not equalised, because `409 EMAIL_TAKEN` on register already tells anyone whether an email is registered, by design.
- **The token's algorithm is pinned to HS256 when it is verified** (02 §4; author's brief). Left open, `jsonwebtoken` also accepts HS384 and HS512 tokens made with the same secret. A test signs one with HS384 and expects 401; it fails when the pin is removed.
- **The `/auth` rate limit covers register and login only, not `GET /auth/me`** (02 §4; author's correction in the unit 3 brief). Why: `/auth/me` runs on every page load, so counting it would use up a normal visitor's 20 requests. Both routes share one counter of 20 per visitor per 15 minutes.
- **Over the limit the API answers `429 RATE_LIMITED` in the standard error shape, and the form shows `Demasiados intentos. Espera unos minutos e intenta de nuevo.`** (02 §4, §7; 03 §5.2; author's correction). Why: the library's default plain-text body would have broken the rule that every error carries a code the interface maps to its own text. The standard `RateLimit` headers (draft 8) are on, so the per-visitor count can be checked from outside.
- **Work unit 3 also builds the welcome and log-in screens and the client session** (01 §15; author's brief). Why: the author wanted auth testable end to end in production in the same unit, instead of waiting for the play screen. A provisional protected `/play` (it calls `/auth/me`, shows the email and logs out) stands in until unit 5. The 25-minute budget covered only the backend part; the session log records the real time.
- **The token lives in `localStorage`** (03 §7). Cost: any script running on the page can read it. The alternative, an httpOnly cookie, needs the frontend and the backend on the same site, and here they are on two different hosts (Vercel and Render). What keeps the exposure small: the app renders no user-generated HTML and loads no third-party scripts. With more time: proxy the API through the Next.js host and switch to a cookie.
- **"Tu sesión expiró" appears only when the server rejects a token** (03 §7, §8; the author's answer to Q1 in `odd/tasks/03-auth.md`). A protected page that finds no token goes to `/login` without the notice. Without a token the app cannot tell a lost session from a visitor who never logged in, such as someone opening a shared `/play` link, and for that visitor the notice would be false.
- **The log-in form turns off the browser's own validation (`noValidate`)** (03 §5.2; A11). The browser's validation bubbles appear in the browser's language, not in the app's Spanish. The API validates, and the form maps `error.code` to the copy of 03 §5.2.
- **`TRUST_PROXY_HOPS=3` on Render, measured on 2026-11-20** (02 §4; unit 3, T3 and T6). One visit to the temporary `GET /ip` with the variable unset showed `req.ip` as `::1`, a proxy on the same host, and an `X-Forwarded-For` of three addresses: the visitor, a Cloudflare edge address (`162.158.x.x`, Render's edge) and a Render-internal address (`10.x.x.x`). The leftmost matched the author's public IP as reported by an outside service. With the variable at 3: `req.ip` became the author's IP; a request carrying a forged `X-Forwarded-For: 203.0.113.7` arrived with four addresses (Render appends after the forged one) and `req.ip` stayed the author's IP, so 3 is not too high; the `/auth/login` limit answered `r=19` for that visitor. A first reading through Cloudflare WARP gave the same count of 3 with the WARP exit address as the visitor. Visitor addresses are left out of this public repo. `/ip` was removed afterwards. The second-network check and the log check for `ERR_ERL_*` are in the production checklist (`odd/tasks/03-auth.md`, Author steps).
- **PENDING, deferred by the author on 2026-11-20: unit 3 follow-ups** (for the README section on improvements, "what I would do next"). Found by the independent verifier (A1–A6) and by the RDD reviews (the rest); none blocks the unit. Each line: what it is, and the fix proposed.
  - **A1, proxy hops untested.** No test pins `TRUST_PROXY_HOPS=3` against a forged `X-Forwarded-For`; since the `/ip` test was removed, setting `trust proxy` to `true` (forbidden by 02 §4) passes all 96 tests. Proposed: a `rateLimit.test.ts` case with 3 hops that sends `forged, visitor, edge, internal` and expects the visitor's counter.
  - **A2, `sub` check untested.** The type check on the token's `sub` in `requireAuth.ts` has no test; without it the answer is still 401, through `findById`. Proposed: a test with a correctly signed token whose `sub` is missing or numeric, expecting 401.
  - **A4, no email length cap.** A 5,005-character address registers with 201. Proposed: `.max(254)` in the credentials schema of `routes/auth.ts`, with a 400 test.
  - **A5, welcome flash.** A signed-in visitor sees the welcome screen for an instant before going to `/play` (03 §5.1 says "straight to"); no protected content shows. Proposed: render the welcome only once the auth state is known, or accept the flash in this file.
  - **A6, case-sensitive `Bearer`.** `bearer <token>` gets 401, while HTTP authentication schemes are case-insensitive; our frontend always sends `Bearer`. Proposed: match the prefix case-insensitively in `requireAuth.ts`.
  - **Readability, the `expired=1` query.** It is a constant in `lib/api.ts` but literal key and value in `login/page.tsx`; changing one side silently drops the notice. Proposed: one shared key and value read by both.
  - **Readability, error copy typing.** `copy.login.errors` is typed `Record<string, string>`, so a misspelled code compiles and falls back to the generic message. Proposed: `Partial<Record<ErrorCode, string>>`.
  - **Readability, `themeColor`.** `layout.tsx` repeats the paper hex instead of sharing the `--color-paper` token. Proposed: a shared constant, or a comment in `globals.css` pointing to the layout.
  - **Hop count log line.** The effective `TRUST_PROXY_HOPS` is not visible at runtime; an unset variable shows only as an `express-rate-limit` warning after the first `/auth` request. Proposed: print the hop count in the boot line of `index.ts`.
  - **Checklist order (R2-001).** Item 7 of the production checklist repeats items 1, 3 and 4 after item 4 has used up the network's 20 attempts, so the limit can look broken. Proposed: fold the 390 px and Shields conditions into items 1–4, or move the limit item last and state the 15-minute wait.
  - **Checklist item 1 guidance (R2-002).** Its failure text merges "no token" (plain `/login`) and "token rejected" (`/login?expired=1`). Proposed: tell the reader to look at the URL and the notice to tell them apart.
  - **02 §4 check (R2-003).** 02 §4 still asks to compare `req.ip` from two networks, which nothing shows since `/ip` was removed. Proposed: say the check now reads the `RateLimit` remaining count from two networks (checklist item 4).

## 2026-11-20 — Work unit 4 (`odd/tasks/04-rounds.md`)

- **The anonymity of a round was attacked on paper before any code** (author's brief; vectors V1–V16 in `odd/tasks/04-rounds.md`). Each way the stock or the date could leak before a decision is covered by a test, closed by the design, or accepted. None needed a change to the 02 §7 contract.
- **Two accepted limits added to 01 §12.** Matching a chart's shape against public prices of the public universe; and the response time of creating a round, which depends a little on the stock's history. Why accepted: the first cannot be closed without distorting the chart, and the second is one noisy sample per round.
- **02 §7 made precise, same contract.** A non-UUID round id answers the same `404` as an unknown or foreign one, so no answer tells whether a round exists. An invalid decision body is rejected before anything is read. Resuming reads exactly 252 closes. `GET /stats` counts decided rounds only, because an open round's frozen return counted in "buy everything" would reveal its direction.
- **The SQL of the rounds was run against a throwaway local Postgres before the push** (unit 4, T7). The repository tests use in-memory fakes, so they cannot see SQL errors. A scratch script ran the real app and repositories on a local Postgres 16 with `001_init.sql`. It found that the resume query used `window`, a reserved word, as an alias: resuming a round failed (fixed in `964ce93`). It then confirmed the partial-index race, the frozen return at six decimals, the reveal against the stored row, the idempotent second decision and the three identical `404`s.
- **PENDING, from the RDD review of unit 4 (non-blocking, approved)** (for the README section on improvements). Each line: what it is, and the fix proposed.
  - **An open round can get stuck** (resilience and reliability). If a series refresh ever left fewer than 252 closes up to an open round's cutoff, every `POST /rounds` for that user would answer `500`. With no rerolls, the user could not play until someone edited the database. Proposed: when the window cannot be rebuilt, void that round (marked and kept out of stats) and open a new one, logging the event without the symbol; and make the seed refuse a refresh that shortens a symbol with open rounds.
  - **A comment overstates `closes.upTo`.** It says "always `count` rows", but a short series returns fewer, and the callers' length checks depend on that. Proposed: "at most `count` rows: a fixed-size read; callers check the length".
  - **The no-leak test helpers are copied in two test files.** The decision tests also skip the header and log checks. Proposed: one shared helper module, and the same header and log checks on the decision path.
  - **`ApiError` now passes through for any status,** and every 5xx is logged as "Unavailable". Proposed: limit the pass-through to the listed codes (503 `NO_DATA` for now), or state the general rule in the class comment, and label the log by code.
  - **The frozen return has two names:** `r` in `DecidedRound` and `forwardReturn` everywhere else. Proposed: `forwardReturn` everywhere.
  - **`L` and `H` read as opaque letters** where they are imported. They are the names 02 §6 uses. Proposed: `SHOWN_DAYS` and `HORIZON_DAYS` at the use sites, keeping the spec's letters in the domain file's comments.
  - **The repository SQL has no automated test** (reliability). It was run by hand this unit (entry above). Proposed: an opt-in `pnpm test:db` against a local Postgres named by an environment variable, outside the default `pnpm test`, which stays without network or database.

## 2026-11-20 — Work unit 5 (`odd/tasks/05-play.md`)

Design points 03 did not define, each settled the simplest way (author's brief):

- **Until `GET /stats` exists, the top bar shows only the streak, and only after the first decision of a page load** (03 §5.3; unit 6 brings the round count, the stats link and log-out). The decision response carries the streak; before any decision there is no number to show, and a `0` would be false for a returning player.
- **The chart is drawn in the pixels of its own box** (03 §6). A `ResizeObserver` measures it, so lines, dots and text stay sharp from 320 to 480 px without stretching an SVG. The ink line still has `vector-effect: non-scaling-stroke`.
- **The reveal sequence is CSS keyframes whose last frame is the element's normal style** (03 §6, §4). With `prefers-reduced-motion: reduce` the animations are off and the final state shows at once; no JavaScript timers.
- **The bottom panel keeps the reveal card's height in every state** (03 §10). The question and the buttons sit at the bottom of it, so the chart is the same size sealed and revealed (measured: 280 px in both at 390 × 664), and one empty line is reserved for the (P1) live price. The cost is empty space above the question before the decision.
- **The page is `100svh` tall,** the visible height with the browser's bars showing, so both buttons are on screen without scrolling (measured at 390 × 664).
- **Labels on the revealed chart:** start date left, cutoff date right-aligned to the cutoff, end date at the right edge; each price just above its dot (below it when the dot is at the top). There is no collision avoidance, so the end price can sit on top of the future line.
- **The headline arrow is `▲` above zero and `▼` below; at exactly zero there is none,** and `0.0%` is shown alone. The arrow's accessible name is `Subió` or `Bajó` (03 §10).
- **The `aria-live` region is always on the page and only filled at the reveal,** with the arrow's word, the percent and the call line, because a region added together with its text is often not read out.
- **Hover styles apply only on devices that can hover.** On a phone, `:hover` stays on the last button tapped, which left `Siguiente gráfica` underlined after a decision.
